# 2026-09-10 — Sibuyan Alert

## Codebase MVP analysis

Performed a full read-only audit of the monorepo and assessed it in MVP terms.

**Facts established**
- Monorepo: `client/` (Vite + React 18 + MapLibre GL + Tailwind, wouter wrapper) + `server/` (Express + Mongoose + Socket.IO + GridFS).
- Size: ~31.7k LOC client product code, ~13.2k LOC server product code (~45k total), plus ~23.3k LOC tests.
- 119 client source files / 81 client test files; 61 server source files / 43 server test files. ~879 `it()/test()` declarations.
- 142 commits, first on 2026-03-07 ("Initial local snapshot"), "MVP" commit on 2026-03-08. Development is heavily back-loaded: most work July–Sept 2026.
- API surface: ~46 routes across auth / reports / admin / files / notifications / high-risk-zones / analytics.
- Roles: `ordinary`, `reporter`, `municipal_admin`, `responder`. Municipal scoping to Cajidiocan / Magdiwang / San Fernando. No super-admin by design.
- Report lifecycle: pending → verified | rejected | transferred → responding → resolved.
- `server/.env` and `server/uploads/**` are NOT tracked by git (good). `server/coverage/**` IS tracked (build artifact committed — hygiene issue).

**Verdict reached**
- The core loop (report → verify → respond → resolve on a map) is complete, hardened, and production-shaped. This is not a fragile MVP.
- But scope is roughly 4–6x a true MVP. Only ~15–20% of the code is the irreducible loop; the rest is v1.5/v2 capability (transfer+ack, multi-unit response, web push, analytics + Excel/CSV export, high-risk zones + 3D map, session manager, face-redaction pipeline, PMTiles, Redis adapter).
- Biggest MVP *gaps* (things a minimum product for this domain needs): no offline/SMS fallback despite the stated low-connectivity context; KYC-gated reporting creates a cold-start failure (no admin online ⇒ nobody can report); no super-admin recovery ⇒ a municipality can be locked out.
- Main debt: god controllers (`adminController.js` 1766 LOC, `reportController.js` 1262 LOC), legacy dual fields in `Report.js` (accidentTime/incidentTime, respondedBy/responders, locationSource/locationCapture), duplicate ImageViewer components.

No files were modified during the audit itself.

## Implemented: duplicate-incident detection (MVP gap #4)

Chose a **warn-then-confirm** design over hard blocking: a hard 409 would be a false-positive lockout on the emergency path, and the reporter is the only one who can tell two nearby crashes apart.

**New files**
- `server/utils/duplicateDetection.js` — pure, dependency-free matcher. Exports `findDuplicateCandidates`, `distanceMeters`, `DUPLICATE_WINDOW_MINUTES` (60), `DUPLICATE_RADIUS_METERS` (250), `MAX_DUPLICATE_CANDIDATES` (5). Local haversine so utils stay free of model/service imports. Incident type is a signal (`typeMatch`), deliberately NOT a gate — a false prompt costs one click, a missed duplicate costs a dispatch. Excludes `rejected` reports.
- `server/tests/duplicateDetection.test.js` — 13 unit tests.
- `server/tests/duplicateReportGuard.test.js` — 7 controller-level tests (409 path, no upload on 409, override records `possibleDuplicateOf`, distant candidate does not warn, rejected candidate does not warn, lookup failure never blocks).

**Modified**
- `server/models/Report.js` — added `possibleDuplicateOf` (ObjectId ref Report, default null), set only when the reporter overrides a warning, so admins get an audit trail.
- `server/controllers/reportController.js` — added `findRecentDuplicateCandidates` (bounding-box pre-filter, `.limit(25).lean()`, wrapped in try/catch so detection can never block submission) and the guard in `createReport`. Guard runs BEFORE any GridFS upload so a rejected duplicate costs nothing.
- `server/middleware/validate.js` — `confirmDistinct` must be `'true'` or `'false'` (multipart strings).
- `client/src/pages/ReportPage.jsx` — split submission into `buildSubmitData` + `submitReport` (FormData cannot be replayed, so it is rebuilt for the confirm resubmit); 409 `POSSIBLE_DUPLICATE` opens a confirmation Modal listing nearby reports with distance/age/status, and resubmits with `confirmDistinct: 'true'`.

**Verified**: server 44 files / 239 tests pass (was 42 / 219), client 80 files / 683 tests pass, `npm run lint` 0 warnings 0 errors, `npm run build` succeeds.

**Deliberate non-goals** (kept out to stay MVP): no admin-side merge/dismiss UI, no cross-municipality duplicate detection, no fuzzy text matching, no auto-merging.

## Verified: the "no offline / SMS path" gap (MVP gap #1)

Confirmed against the code rather than assumed:

- `client/public/sw.js` (71 lines) has **no `fetch` handler** — push + notificationclick only. Zero offline caching.
- The SW is registered lazily in `client/src/services/pushNotifications.js:39`, so it is not even active unless the user opts into push.
- **`client/public/manifest.json` does not exist.** `client/public/` contains only `cascades/`, `icons/`, `maps/`, `sw.js`. There is no `<link rel="manifest">` in `client/index.html` either. `CODEBASE_CONTEXT.md:80` documents `public/manifest.json` as if it existed — **the doc is wrong**, and the app is therefore not installable as a PWA. On iOS this means Web Push can never reach a responder, since iOS requires an installed home-screen web app for push.
- No SMS provider in any `package.json` (no twilio / semaphore / movider / vonage / infobip).

**Important nuance** (corrects an overstatement): notifications ARE persisted server-side. `Notification.createAndSend` writes a MongoDB record (30-day TTL) and `GET /api/notifications` exposes a feed. So an offline responder is not permanently blind — they see the alert *when they reconnect*. The real defect is that **nothing pages them**: every channel is pull-based or requires a live device, so the alert arrives late instead of now.

**Fix ordering if pursued**: (1) SMS gateway to the responder's phone — the only channel that survives "limited telecommunications"; (2) SW `fetch` handler + app-shell cache + IndexedDB report queue for the reporter side; (3) server-side undelivered-alert replay on reconnect (partly exists already via the notification feed).

### User decision: SMS is OUT of scope (declared delimitation)

The user confirmed "no SMS" is already in the capstone's **delimitations**, so SMS recommendations are not actionable. Pivoted to IP-only paging alternatives.

Additional findings gathered while re-scoping:

- **No escalation logic exists anywhere in the server.** A repo-wide search for escalat/unacknowledged/reminder/re-alert matched only one comment in `adminController.js:662` about transfers. The acknowledge-and-escalate loop is genuinely absent — a real gap, not a duplicate of something present.
- **Push permission is only requested from an explicit Settings toggle** (`AuthContext.jsx:262`, `subscribeToPush({ requestPermission: true })`). The login path uses `requestPermission: false`, so a responder who never opens Settings is never asked and silently receives no push.
- **`sw.js` has no `pushsubscriptionchange` handler**, so when the browser rotates a push subscription the server keeps a dead endpoint and delivery stops silently.
- `AuthContext.jsx:348` unsubscribes when `notificationPreferences.browserPush === false`; the silent login sync lives at `AuthContext.jsx:357-361`.

**Recommended (SMS-free) order**: (1) fix Web Push so it works at all — manifest + `pushsubscriptionchange` + sensible permission timing; (2) acknowledge-and-escalate loop reusing `PUT /api/reports/:id/respond` as the ack, with a 5-minute no-ack re-alert and admin flag; (3) visible connection state so failure is never silent; (4) offline-first responder view (SW `fetch` cache + IndexedDB snapshot); (5) offline report queue with an idempotency key (pairs with the duplicate detection built above); (6) field pre-load before dispatch.

## Database audit + performance implementation

**Audit findings (all verified against source, not assumed).** The headline correction: the admin queue cost **16 round trips per page load**, not the 10 I first estimated (1 find + 8 populate + 1 total count + 6 separate status counts).

Critical discoveries:
- **No compression middleware at all** — not in `server.js`, not in `package.json`.
- **No index on `reporter`** → `getMyReports` was a full collection scan.
- **No index on `incidentTime`** → both the admin queue and the public map paid a blocking sort (32 MB cap).
- **`analytics_view` is a MongoDB *view*, not materialised** — it re-executes on every read and is referenced **nowhere** outside its own service. Zero references in controllers/services/utils.
- **No server-side caching of any kind**, on a public unauthenticated `/api/reports/stats` that ran 5 queries (2 aggregations).
- **No `maxTimeMS` anywhere** — no query timeout in the codebase.
- **ETags existed only on files/evidence**, never on JSON endpoints.

**Implemented**
- `server/config/queryPolicy.js` (new) — `maxTimeMs` 5000, `clampPageSize`/`clampPageNumber`, `CACHE_TTLS`, `CACHE_MAX_ENTRIES`. Env-overridable with safe fallbacks.
- `server/utils/apiCache.js` (new) — cache-aside with **in-flight dedup** (stampede guard), **errors never cached**, prefix invalidation, bounded size, `getCacheStats()`.
- `server/utils/httpCache.js` (new) — `buildWeakEtag`, `etagMatches` (RFC 7232, weak prefix + `*` + lists), `sendConditionalJson`. Sets `Vary: Cookie, Accept-Encoding` — without `Cookie` a shared cache could leak one session's data to another.
- `compression` dependency added; middleware registered in `server.js` before the body parsers with `threshold: 1024` and a double-encode guard.
- **Indexes added**: `{reporter:1, createdAt:-1}`, `{status:1, incidentTime:-1}`, `{municipality:1, status:1, incidentTime:-1}`, `{status:1, updatedAt:-1}` on Report; `{isActive:1, createdAt:-1}` on HighRiskZone (replacing the redundant single-field index).
- **Admin queue 16 → 7 round trips**: dropped 4 populates that only the dossier view needs, added `.lean()`, replaced 6 `countDocuments` with one `$group`, added `maxTimeMS`.
- **Hazard zones**: `.limit(500)` + cache + server-side severity sort + `invalidate('zones:island-wide')` on all three mutations.
- **Public reports**: `?since=` delta sync, `syncCursor` in the response, `maxTimeMS`, ETag via `sendConditionalJson`.
- **Stats**: wrapped in `getOrSet` with `invalidate('stats:')` on verify.
- **Search**: `MIN_SEARCH_LENGTH = 3` guard. Deliberately did NOT add a `$text` index — it matches whole words only and would be a UX change, not a drop-in. Documented as a trade-off.
- **`analytics_view`**: resolved by *correcting the documentation* rather than materialising. Caching solves the actual performance concern; a `$merge` rollup would add a second source of truth and staleness for no benefit. The service doc now states plainly that a view gives privacy scoping, not acceleration.

**Verified**: server 46 files / 273 tests (was 45/254), client 82 files / 690 tests, lint 0/0, build succeeds.

**Test-fixture note**: adding `.maxTimeMS()`/`.lean()`/`aggregate()` to the query chains broke `adminReportDeepLink.test.js` and `globalHighRiskZones.test.js` — both needed their mock chains extended. `apiCache` is module-global, so tests touching cached endpoints must call `__resetCacheForTests()` in `beforeEach`.

**Known remaining gaps** (documented, not implemented): `.skip()` is still O(n) at depth (keyset pagination is next), `countDocuments` still runs per paginated request, and the client `queryCache` is memory-only.

## Data-handling audit (source → UI)

Traced every field from the Report document through the serializers, the API payload, the client utils, and into the rendered UI.

**CRITICAL — `responderAgency` enum mismatch (respond fails with 500).**
`Report.responders[].unitType` enum has 7 values (`MDRRMO, PNP, BFP, Medical Team, RESCUE, MEDICAL, BARANGAY`) and `respondToReport` validates against all 7. But the legacy `Report.responderAgency` enum has only **4** (`PNP, MDRRMO, Medical Team, BFP, null`). `adminController.js:1343` does `report.responderAgency = unitType` when the responder is first, so a **BARANGAY / MEDICAL / RESCUE first responder throws a Mongoose ValidationError → 500**, and the respond never lands. The client explicitly offers these: `ResponderUnitModal.jsx:12-13` has "Barangay Rescue Unit" (BARANGAY) and "Medical Response Team" (MEDICAL). Locations: `server/models/Report.js:304-308` vs `:279-283`, `server/controllers/adminController.js:1268` and `:1343`, `client/src/components/ResponderUnitModal.jsx:12-13`. Interaction with the new escalation engine: a failed respond means the incident stays unacknowledged and will escalate.

**HIGH — casualties coerced to 0, destroying "not recorded".**
Both serializers force null/undefined to 0 (`publicReport.js:1-4` `toNonNegativeInteger`; `operationalReport.js:107-111` `Number(x) || 0`). The client has real logic for the unrecorded case — `formatCasualtyMetric` returns `'Not recorded'` and `MapIncidentDetails.jsx:321` renders a not-recorded message guarded by `typeof injured !== 'number'` — but the guard can never be true because the server always sends numbers. Net effect: an incident with no casualty data displays as "0 injured, 0 fatalities, 0 missing", which reads as a positive assertion that nobody was hurt.

**MEDIUM — public feed drops transfer provenance, so the wrong municipality is shown.**
`getPhysicalMunicipality` (`client/src/utils/incidentDetails.js:102-112`) resolves origin via `originalMunicipalityName` → `transferHistory[0]` → `transferTrail[0]` → `municipalityName`. `toPublicReport` exposes **none** of the first three, so public users fall through to `municipalityName` — which transfer rewrites to the *handling* office. Operational users get `originalMunicipalityName` + `transferTrail` and see the correct value. Same helper, two different answers depending on which endpoint the user hit. Locations: `server/utils/publicReport.js:139-173`, `AccidentHistoryPage.jsx:1007,1013,1052`.

**MEDIUM — operational feed drops `respondingAgencies`, so admins see fewer units than the public.**
`toOperationalReportSummary` has `responderAgency` (first responder only) but no `respondingAgencies`. `getRespondingAgencyText` falls back to `respondedBy.agency` / `responderAgency`, both of which describe only the FIRST unit. Public users get the full multi-unit set. The inconsistency runs backwards — the people coordinating see less.

**LOW — incident type label differs between input and display.**
The report form (`client/src/components/report/reportConfig.js:5-11`) labels types as "Vehicular collision", "Hit and run / pedestrian", "Mechanical failure". Every display path instead regenerates the label from the raw enum via title-casing, yielding "Vehicular", "Pedestrian", "Mechanical". The "hit and run" nuance is lost. Aggravating factor: `formatIncidentType` is **duplicated in 3 files** (`MyReportsPage.jsx:71`, `DashboardMapWorkspace.jsx:46`, `ReporterDashboardPage.jsx:55`) with slightly different fallback strings.

**Verified CLEAN (checked, no issue found):** the 7 incident types match exactly between `server/config/incidentCategories.js` and `client/src/components/report/reportConfig.js`; `viewCount` is correctly present in the operational summary and the Views field is gated behind `canViewFullDetails`, so admins do receive it (I initially suspected a gap here and cleared it); `getRespondingAgencyText` has a working fallback chain; `toOperationalReportSummary` correctly omits fields only the dossier view needs.
