## Logo replacement — COMPLETE

Replaced the Sibuyan Alert brand mark with a vector replica of the supplied
`C:\Users\User\Pictures\logo\final-logo.jpg`.

**Method that worked:** measure the raster with Pillow, build an SVG in the *source* coordinate
space (1024²) so measurements map 1:1, rasterise with `sharp`, then compare numerically
(row/column band scans of both images) and iterate. Three passes got the ring within ~1px and the
glyph/base within a few px. Pure eyeballing would not have caught the triangle being 68px too
narrow or the base crescent being 30px too thin.

**Measured geometry (source raster):**
- ring centre `(506, 408)`, outer radius `323`, inner radius `255` (band 68)
- tail is a **tangent-line teardrop**: tangent points `(285,646)`/`(727,646)`, tip `(506,852)`.
  The lines are genuinely tangent — verified by computing the perpendicular distance from the
  centre to the fitted tail line (325 vs R=323).
- inner void closes at `(506,648)`: the tail is **solid**, so the band thickens downward and the
  void is NOT a uniform offset of the outer path.
- warning triangle: apex `(603,242)`, base `(513,390)-(692,390)`, base bows down to y≈401
- alert arcs: centred on the triangle, radii `110.7` (inner) and `158` (outer), stroke ~23
- colours: gradient `#33568f → #1a2a5c`, glyph `#800000`

**Source is slightly asymmetric** (AI-generated: the right leaf/crescent sit ~50-70px lower than
the mirrored left). I deliberately built the vector **symmetric about x=506** — the user asked for
something "clean and scalable", and the asymmetry is an artifact rather than intent. This is noted
in the SVG comment.

**Assets written to `client/public/icons/`** (all RGBA PNG, matching the files they replace):

**`Alert.png` was the important one** — it is the *in-app* brand mark (`MainLayout` sidebar,

**SVG source of truth kept** at `client/src/assets/brand/sibuyan-alert-mark.svg` so any size can be
regenerated. Render/export scripts live in `scratch/logo-work/` (`render.mjs`, `export.mjs`,
`preview.mjs`) — run with
`NODE_PATH=C:/Users/User/.workbuddy-ai/binaries/node/workspace/node_modules <node> <script>`.

**apple-touch-icon fixed (was the flagged follow-up).** `index.html` pointed
`apple-touch-icon` at `icon-192.png`, which is transparent — and iOS renders transparent
apple-touch-icon pixels as **black**, so the new mark would have shown a black box on an iOS home
screen. The old logo had the same latent bug but was a filled circle so it barely showed; the new
one has much more transparent area, which would have made it obvious. Added
`client/public/icons/apple-touch-icon.png` (180×180, **fully opaque** white, artwork at 78% so
iOS's squircle rounding never clips it) and repointed the tag with `sizes="180x180"`. Comment added
in `index.html` warning not to repoint it back at the transparent icons.

Verified by simulating the iOS squircle mask over the exported file — renders on white, no black.
Convention now: `icon-192/512` transparent (purpose `any`), `maskable-512` opaque (safe zone),
`apple-touch-icon` opaque 180² (iOS), `Alert.png` transparent 500² (in-app brand mark).

## Bonus bug found while auditing logo references: broken push-notification icon

Swept the whole repo for remaining icon references and found a real defect in the **server**:

`server/controllers/adminController.js` lines 1441 and 1567 both set `icon: '/icon-192x192.png'`.
**That file has never existed** — the shipped asset is `/icons/icon-192.png`. `pushService.js` only
applies its default when `payload.icon` is falsy:

```js
icon: payload.icon || '/icons/Alert.png',
```

so the bad path won every time. The two affected notifications (post-respond "Help is on the way"
and "Incident Resolved") rendered without the app icon. Silent failure — a 404 in an image field
breaks nothing visibly in the logs.

**Fixed** both to `/icons/icon-192.png`.

**Guard added:** `server/tests/iconAssetPaths.test.js` — walks `server/**/*.js` (excluding tests),
extracts every quoted root-relative image path (`'/…\.png|jpg|svg|webp|ico|gif'`, requiring the
leading quote so absolute URLs can never match), and asserts each resolves inside `client/public/`.
Verified by reintroducing the bug: the test fails and names the file and both paths. This is the
kind of check that pays for itself — a path typo in an image field is otherwise invisible.

**Lesson worth repeating:** when replacing a brand asset, grep the *whole* repo — including the
server and service worker — not just the frontend. The frontend was fully consistent; the breakage
was server-side.

**Deliberately NOT changed:** the favicon still points at `/icons/Alert.png`. That is fine and
arguably optimal — `Alert.png` is needed anyway as the in-app mark, so one cached download serves
both, and it is now 53KB instead of the previous 529KB.
