## New reusable component: `RiskZoneMarkerPin` (red pulsing risk-zone pin)

**Request:** a reusable React + Tailwind component for a red "Risk Zone Marker Pin" —
solid pure-red core dot (no white border/outline), continuous smooth ripple radiating
outwards, strictly monochromatic red (transparent red fades only), pure-Tailwind
animation, props `size` (sm/md/lg) / `pulseSpeed` / `className`.

**Files:**
- NEW `client/src/components/map/RiskZoneMarkerPin.jsx` — named + default export,
  no React import (new JSX transform), `...props` spread with `style` merged the way
  `components/ui/Skeleton.jsx` does it.
- MODIFIED `client/tailwind.config.js` — added to `theme.extend`:
  - `animation['risk-ripple'] = 'riskRipple var(--risk-ripple-duration, 2s) cubic-bezier(0.22, 0.61, 0.36, 1) infinite'`
  - `keyframes.riskRipple` = 0% `scale(.32)/opacity .85` → 70% `opacity .28` → 100% `scale(1)/opacity 0`

**Design decisions worth keeping:**
- Palette is **red-600 core + red-500/40 waves** only. In this repo those hexes are
  identical to `alert-500`/`alert-600`; the hazard pin must stay red so it never reads
  as an operational status pin (blue/amber/violet/cyan/green — see
  `src/utils/mapMarkerVisuals.js` `STATUS_PIN_PALETTES`).
- **Why a CSS variable and not a class:** `pulseSpeed` is a runtime prop, and Tailwind's
  JIT extracts class names by scanning literal text — a template literal like
  `` `[animation-duration:${s}s]` `` would never be emitted. So the cycle length rides on
  `--risk-ripple-duration` (set inline on the root) while the animation itself stays a
  Tailwind utility (`motion-safe:animate-risk-ripple`).
- `pulseSpeed` is a **multiplier** (1 = 2s/cycle), not seconds.
- Wave delays are **negative** (`-(i * cycle) / count`) so the ripple is already
  continuous on frame 1 — no dead opening beat. This mirrors the existing
  `.report-marker__pulse--delayed` idea in `src/index.css` (0.5s offset on a 1s sweep).
- `prefers-reduced-motion`: ripples get `motion-reduce:hidden`, the red core stays.
- Footprint = ripple diameter (not the dot), so nothing overflows the component box.

cleanly; real Tailwind CLI build (`tailwindcss -c tailwind.config.js -i src/index.css`)

**Design decisions worth keeping:**
- **Anchor matters:** `anchor: 'bottom'` was correct for a teardrop but offsets a symmetric
  radar dot by half its height. Zone markers are `'center'` now; do not "fix" it back.
- **Stagger = negative `animation-delay` computed in JS, not CSS classes.** JS owns both the
  cycle length and the per-wave phase so they cannot drift: `delay_i = -(i * T) / N`, rounded
  via `Number(x.toFixed(3)) || 0`. The `|| 0` is deliberate — it normalises the first wave's
  `-0` to a plain `0` (`` `${-0}` `` is already `"0"`, but `toFixed` would yield `"-0.000"`).
- **Single source of truth for the duration:** JS writes `--zone-radar-duration` inline and
  CSS consumes it via `var(--zone-radar-duration, 2.4s)`. Same reasoning as
  `--risk-ripple-duration` above (Tailwind JIT cannot emit template-literal arbitrary values).
- **No `will-change`.** Only `transform: scale()` + `opacity` animate, which the compositor
  promotes on its own. A permanent `will-change` would cost one layer per wave *per zone*
  for zero benefit — this was a deliberate rejection of the "add will-change for GPU" reflex.
- **`prefers-reduced-motion` fallback keeps one ring visible** (`opacity .28`, `scale(1)`) and
  hides waves 2-3 via `.zone-marker__ripple:nth-child(n + 2)`. The compound selector is safe:
  the core is child 4 but lacks the `__ripple` class, so it is not matched.
- **Removed a white accent that violated the spec:** `.zone-marker.is-selected` /
  `.zone-marker.map-marker--selected` used to inherit `drop-shadow(0 0 6px rgba(255,255,255,.95))`
  from the shared `.report-marker.is-selected` rule. That rule is now split — incident pins keep
  the white kicker, zone markers get a red-tinted glow.

## ROOT CAUSE FOUND — user's Brave browser has `prefers-reduced-motion: reduce` active

**How it was proven.** The user supplied a screen recording
(`C:\Users\User\Videos\Captures\Sibuyan Alert - Brave 2026-09-15 13-02-04.mp4`, 18.73s,
1920x1080, ~27.6fps). No ffmpeg on the box, so: created the managed venv, installed
`imageio-ffmpeg` (ships a static ffmpeg 7.1) + `numpy`, then
`ffmpeg -vf fps=8,crop=1520:600:400:480 -pix_fmt rgb24 -f rawvideo audit.raw`
(150 frames) and analysed with numpy.

- **Alpha profile is bit-identical across time.** At t=0.00s, 2.50s and 5.00s the radial
  alpha profile matched to 3 decimals at every radius (e.g. `18:0.584`, `25:0.308`,
  `40:0.054`). A live 2.4s cycle over 5s would produce wildly different profiles.
- **halo_r / core_r = 40.0 / 12.9 = 3.10.** The CSS ratio is 36px ripple / 12px core =
  **3.00**. The browser page was at ~2.15x zoom (12.9 / 6 = 2.15), which also puts the
  18px CSS ripple radius at 38.7px ~= the measured 40px. Exact match for a ripple frozen
  at `scale(1)`.
- **The disc is hard-edged**, confirmed at 5x zoom — a crisp circular boundary, not a
  blur. And it is **translucent (~0.28)**, not opaque: if the animation were merely dead
  with the CSS loaded, the ripple would render at its base `opacity: 1` -> an opaque disc.
  Translucency + only ONE ring per marker (ripples 2-3 absent) is the reduced-motion
  override signature (`opacity: .28`, `transform: scale(1)`, others `display: none`).
- 40-frame contact sheet (t=0..4.9s) shows every tile identical.

**Cause chain:** Windows "Animation effects" OFF (Settings -> Accessibility -> Visual
effects) -> `SPI_GETCLIENTAREAANIMATION` = 0 -> Chromium/Brave reports
`prefers-reduced-motion: reduce` -> our reduced-motion block renders a static marker.
`reg.exe` is on the sandbox program blacklist so the registry could not be read directly
to confirm; the browser-side evidence is conclusive regardless.

**Fix applied** (`client/src/index.css`): under reduced motion the marker no longer goes
fully static. The expanding `scale()` animation is the vestibular trigger, so it is
removed and the rings are pinned at fixed sizes (`scale(1)` / `scale(0.6)`), but they now
run a slow **opacity-only** breathe — `@keyframes zoneRadarBreathe`, 3s ease-in-out
infinite, peak driven per ring by `--zone-breathe` (0.26 / 0.36) so the two rings keep
their depth. Opacity cross-fades are widely accepted under reduced-motion guidance.

Verified with `scratch/radar-reduced-probe.html` in headless Chrome (headless forces
reduce, so it exercises this exact branch):
`ripple1 name=zoneRadarBreathe playState=running iterations=infinite opacity=0.117
transform=matrix(1,...)`, `ripple2 ... opacity=0.162 transform=matrix(0.6,...)`,
`ripple3 display=none`. The `calc(var(--zone-breathe) * .45)` inside the keyframes
resolves correctly (0.26*0.45=0.117, 0.36*0.45=0.162) — confirmed in the built CSS too.
`npm run build` ok, `npm run lint` 0/0, `npm run test:client` -> 84 files / 715 tests pass.

**Gotcha worth remembering:** `animation: <name> <dur> ... !important` inside the media
query resets `animation-delay` with `!important`, which beats the per-wave inline
`animation-delay`. Under reduced motion all rings therefore breathe in sync — fine, and
arguably preferable, but do not expect the stagger to survive there.

## The responding pin was invisible on the reporter/guest map — motion-only affordance

**Report:** on the reporter and guest map, the ongoing incident with status `responding` is
"hindi recognizable" — you cannot tell which pin is the live response. User asked for the

**Root cause — a design decision plus reduced motion:**
`mapVisuals.js` (`MAP_ACTIVE_INCIDENT_CONFIG`) and `MapView.jsx` `getReportMarkerColor`
both document it explicitly:

> Public map (reporter/guest): verified, transferred, and responding share one blue
> "active" pin. **Motion (pulse) alone marks the responding pin.** Operational roles keep
> per-status colors.

So on the reporter/guest map the responding pin is the SAME `#2563EB` as a verified pin,
and the expanding rings + beacon hop were the only differentiators. The reduced-motion
block then did:

```css
.report-marker__pulse { animation: none !important; display: none !important; }
.report-marker--responding svg { animation: none !important; }
```

which does not *calm* the marker — it **deletes the state**, leaving a responding accident
indistinguishable from a verified one. Same failure class as the risk-zone bug earlier
today: a `prefers-reduced-motion` branch that removes the only carrier of meaning.

**General lesson worth keeping: whenever an affordance is communicated by MOTION ALONE,
stripping the motion erases the information rather than softening it. Every such affordance
needs a non-motion fallback (a static ring, a shape, a label, or an opacity pulse).**

- `:root { --marker-beat: 0.5s; }` — single source of truth for the rate.
- `@keyframes markerBeat` (1 -> 1.3 at 40%) and `markerBeatSoft` (1 -> 1.22, eased) — the
  reduced-motion variant.
- Both `.zone-marker__core` and `.report-marker--responding svg` use
  `markerBeat var(--marker-beat, 0.5s) cubic-bezier(0.22, 0.61, 0.36, 1) infinite`.

Consequence: `RISK_ZONE_CORE_PULSE_SECONDS` and the inline `--zone-core-pulse` were
**removed from the JS**. The zone builder now only sets `--zone-radar-color` (the per-zone
hue, which genuinely varies); the beat is global. Do not reintroduce a per-marker duration
— that is exactly what would let the two cues drift apart.

**Responding glow reduced from three drop-shadows (up to 34px) to one 7px shadow.** It is
kept, deliberately: it is the only *non-motion* cue that a responding incident is not a

`transform-origin: 50% 100%` on the pin's svg is load-bearing — the pin's tip is also its
map anchor, so scaling from the tip keeps it on the coordinate. Do not change it to 50% 50%.

## Responding halo: static pin + a staggered three-ring wave train

**Request:** the pin pulsing looked bad, so make the pin static and move the pulse to the
background. Also: no simultaneous pulsing — stagger the elements around it so the effect
reads as a sequence, with a smooth transition.

**I asked rather than guessed.** "mga elemento sa paligid nito" was genuinely ambiguous
(rings around the marker vs. neighbouring markers on the map), and the two readings need
very different work. User picked **rings around the marker**. Worth remembering: for rapid
visual iteration, one short question beats building the wrong thing.

**Design now:** the pin never animates. Behind it sit **three soft filled halo rings**,
staggered one beat (0.5s) apart, each on a 1.5s cycle — so a wave leaves the pin every
0.5s while the other two are mid-flight. A single ring can only blink; three give a
sequence.

**`client/src/index.css`**
- `:root` gained `--marker-wave: calc(var(--marker-beat) * 3)` — the train's full pass,
  derived from the beat so it stays in lockstep with the zone dot.
- `.report-marker__halo` is 36px at `top/left: -8px`, animating
  `respondingHaloWave var(--marker-wave)`.
- `@keyframes respondingHaloWave`: `0% opacity .36 scale(.5)` -> `55% opacity .18` ->
  `100% opacity 0 scale(1)`. The middle stop holds brightness so three rings overlap into a
  continuous train instead of three thin blips.
- Reduced motion: `respondingHaloGlow` (opacity only) with the rings pinned at three fixed
  concentric sizes (`0.55 / 0.78 / 1.0`), so the stagger survives with zero size change.

**`client/src/utils/mapMarkerVisuals.js`** — `RESPONDING_HALO_RINGS = 3`; the builder emits
three identical spans for a responding report. The stagger itself stays in CSS.

**TWO non-obvious traps, both hit and both fixed:**

1. **The `!important` shorthand wipes the stagger.** The reduced-motion block replaces the
   animation with `animation: respondingHaloGlow ... !important`, and an `!important`
   shorthand resets `animation-delay`. A plain `animation-delay` longhand loses to it, which
   silently syncs all three rings into one blink and destroys the sequence. The delay rules
   are therefore `!important` too, and they are more specific so they win. This is the
   second time this gotcha has bitten in this project — check it whenever a reduced-motion
   branch swaps an `animation` shorthand.
2. **The ring was hidden behind the pin.** At 28px, a ring starting at `scale(0.5)` is 14px
   wide — narrower than the 16px pin head — so it spent the first half of its travel
   invisible and the wave train barely read. 36px is the smallest size that clears the pin
   head early, and it conveniently matches the high-risk zone halo's own footprint.

**Verified in headless Chrome, both branches** (`scratch/halo-stagger-probe.html`):
```
NORMAL   halo1 respondingHaloWave 1.5s delay=0s   running scale=0.45
         halo2 respondingHaloWave 1.5s delay=-0.5s running scale=0.845
         halo3 respondingHaloWave 1.5s delay=-1s   running scale=0.974
         pin svg name=none  (pin static: true)
REDUCED  halo1 respondingHaloGlow 1.5s delay=0s   running scale=0.55
         halo2 respondingHaloGlow 1.5s delay=-0.5s running scale=0.78
         halo3 respondingHaloGlow 1.5s delay=-1s   running transform=none
         pin svg name=none  (pin static: true)
three distinct delays: true (both branches)
```
Three distinct delays in BOTH branches is the proof trap 1 was avoided.

**Tests updated:** the responding test now asserts exactly three `report-marker__halo`
matches (`toHaveLength(3)`) rather than mere presence, pinning the wave train.

`npm run build` ok, lint 0/0, `npm run test:client` -> 84 files / 715 tests pass.
**Visual reference:** `scratch/halo-wave-phases.png`.
