## High-risk zone pin: radar / ripple pulse, static dot, 18px reach

**Request, in three steps across the session:** turn the risk-zone pin's effect into a
"Radar / Ripple Pulse Effect"; then the dot was too fast, "match the background"; then make
the dot static and keep the pulse in the background; then halve the red background's reach
twice (36px → 26px → 18px).

**Final spec:** a **completely static** solid-red core dot with three pure-red rings
expanding out of it, one leaving every 0.5s over a 1.5s sweep, inside an **18px** footprint.

### `client/src/index.css`
- Deleted the previous design entirely: `.zone-marker__halo` / `--outer` / `--inner` (two
  static rings) are gone from the CSS and the build.
- New `.zone-marker__ripple` (`inset: 0`, filled disc, no border, no white rim) animating
  `zoneRadarRipple var(--marker-wave, 1.5s)`.
- `@keyframes zoneRadarRipple`: `0% opacity .5 scale(.5)` -> `60% opacity .28` ->
  `100% opacity 0 scale(1)`. The start scale is **0.5, not 0.3**, because at an 18px
  footprint the ring has to clear the 8px core on the first frame or the sweep looks like it
  begins half-grown.
- `@keyframes zoneRadarGlow` (opacity-only) for reduced motion; the three rings hold fixed
  concentric sizes `1 / 0.78 / 0.56` so the sequence survives with zero size change.
- `.zone-marker__radar` is **18px** — half the original 36px. The ripple's reach is the
  single biggest thing deciding how much of the map a hazard zone paints over; at 36px each
  zone covered a 4.5x-dot-wide red disc.
- `.zone-marker__core` is now **static** — no `animation`, no `transform-origin`, no
  `will-change`. The dot is the marker's anchor, so a moving centre reads as the pin drifting
  off the coordinate it marks.
- **Deleted `@keyframes markerBeat` and `markerBeatSoft`** — the dot was their last consumer,
  so they became dead the moment it went static. Do not reintroduce a dot animation without
  also reintroducing a keyframe.

**The `!important` stagger trap again (third time in this project):** the reduced-motion
block swaps the animation in with `animation: zoneRadarGlow ... !important`, and an
`!important` shorthand resets `animation-delay` — so the per-ring `nth-child` delays are
themselves `!important` or all three rings sync into one blink. Check this every time a
reduced-motion branch swaps an `animation` shorthand.

### `client/src/utils/mapMarkerVisuals.js`
- `RISK_ZONE_HALO_RINGS = ['outer','inner']` -> `RISK_ZONE_RADAR_RINGS = 3`; the builder now
  emits three identical `.zone-marker__ripple` spans. The stagger stays in CSS.

## Integration check: the three markers together (not changed — needs a decision)

Rendered all three markers side by side with the real built CSS
(`scratch/marker-system.html`, proof `scratch/marker-system.png`). Each had only ever been
verified in isolation, never together on one map.

**Result:** the three are clearly distinguishable at true map scale — red radar, blue wave
train, plain blue pin. No confusion.

**But the parity the user asked for earlier has shifted.** After the zone's reach was cut to
18px, the responding halo is still **36px — twice the zone's reach**:

| Marker | Reach | Why |
|---|---|---|
| Risk zone (8px dot) | **18px** | reduced twice at the user's request |
| Responding pin (16x22 pin) | **36px** | unchanged |

**Do NOT "fix" this by simply shrinking the responding halo to 18px.** The pin head is 16px
wide, so a halo smaller than roughly 32px spends the first half of each wave's travel hidden
behind the pin — the exact trap already hit and fixed once (that is *why* it was set to
36px). Shrinking it means also raising its start scale from 0.5 to ~0.65, which shortens the
travel and makes the wave read as a pop rather than a sweep. It is a real trade-off, not a
one-line change, so it was left alone and reported instead.

The inherent asymmetry: a small dot can carry an 18px radar, but a 16px-wide pin needs
~32px+ before any halo clears its own silhouette.

**Request:** make the accident markers smaller on every map, and guarantee identical size,
style and appearance across all of them.

**Surfaces:** six components mount `MapView` (`DashboardMapWorkspace`,

markers, so the glyph was already shared — the drift risk was the SIZE, which lived as a

**`utils/mapMarkerVisuals.js`**

  four duplicated defaults (`getMapPinSvg`, `getOperationalMarkerSvg`,

- `.report-marker__halo` is positioned with `calc(2px + var(--marker-h) * 0.328 - 14px)` so it

## Guest map: reporter-shaped filters and KPIs, RBAC intact

**Request:** copy the reporter map's filters and KPIs onto the guest map while preserving
RBAC, implemented in MVP terms.

**The RBAC boundary is a single flag.** `getMapExperience` (`config/mapExperience.js`) is the
one place that decides what each role gets, and for a guest the only *data* gate is
`showPendingReports: false`. Everything else a guest would gain was already public:

| Aspect | Guest before | Guest after |
|---|---|---|
| Filters | 6: Active Incidents, Verified, Responding, Transferred, Resolved, Risk Zones | **3: Active Incidents, Resolved, Risk Zones** |
| KPI cards | Active incidents, Active response, Risk zones | **Active incidents, Resolved, Risk zones** |
| Pending | absent (RBAC) | **still absent** |

- **Filters:** new `GUEST_FILTERS` mirrors `REPORTER_FILTERS` minus `pending`. The three
  operational statuses (verified/responding/transferred) are folded into one "Active
  Incidents" tab — the reporter map already made that call because they are operational
  jargon. `OPERATIONAL_FILTERS.public` was deleted (the guest was its only consumer).
- **Why no separate `active` tab for guests:** `getFilteredMapReports` shows `all` and
  `active` resolve to the SAME set — pending is the only difference between them, and guests
  are never sent pending rows. So `all` *is* the active set, which is why it keeps the
  "Active Incidents" label instead of the reporter's "All open".
- **KPIs:** `public-responding` (Active response) was a subset-duplicate of Active incidents
  — the reporter map's own comment says so — so it was replaced by `public-resolved`, the
  same card the reporter shows. **No new data is exposed**: guests already had a Resolved
  filter tab, so resolved rows were always public. `reporterResolvedReports` was renamed
  `resolvedMapReports` and is now shared by both role sets.
- `public-active`'s `mapFilter` changed from `'incidents'` to `'all'` because `'incidents'`
  is no longer a tab in the guest rail; the hazard layer stays hidden either way, since only
  `'risk-zones'` reveals it.

**Bug hit and fixed:** `resolvedMapReports` was first declared next to the reporter metrics,
*below* `publicMetrics` which reads it — a `const` referenced before its declaration throws
rather than reading as undefined, so all 44 dashboard tests failed at once. It now sits above
both metric arrays. When a render throws, suspect declaration order before suspecting logic.

**Tests:** 4 updated in `DashboardMapWorkspace.test.jsx` + 1 in `mapExperience.test.js` + 2 in

## Admin map UX audit (findings only — nothing implemented)

Asked for MVP UX improvements on the municipal-admin map. Findings verified in code, not
inferred from the screenshots:

1. **The admin camera opens island-wide.** `reporterHomeFocus` in `DashboardMapWorkspace`
   starts with `if (!isReporter || ...) return null`, so only reporters get
   `getMunicipalityMapFocus(user.assignedMunicipality)`; admins and responders fall through to
   `SIBUYAN_CENTER` in `MapView`. The page is titled "Cajidiocan incident map" and promises
   "in Cajidiocan", but the admin sees the whole island — so the incidents they are meant to
   triage are off-screen. Same three-line fix as the reporter path.
2. **`admin-dispatchable` widens the map instead of narrowing it.** The card counts
   verified + transferred (`dispatchableReports`) but carries `mapFilter: 'all'`, so clicking
   "Verified / transferred 1" filters the map to all 4 active incidents. The panel gets the
   right records; the map does not.
3. **The status-filter rail is not sticky** (`hidden lg:flex ... border-b`, no `sticky`), so it
   scrolls out of view before the KPI strip — the filter context is lost exactly when the
   counts are read.
4. **`MapLegend.jsx` is dead code.** Nothing imports it (`grep MapLegend` finds no consumer),
   so the map has no key for the pin colours; the filter rail's dots are the only legend.
   Either render it or delete it — same call as `RiskZoneMarkerPin.jsx`.
5. **Two vocabularies for one dataset.** The rail splits Verified / Transferred / Responding;
   the KPI strip merges Verified + Transferred and scopes Resolved to *today*, so the rail's
   "Resolved 2" sits beside the card's "Resolved today 0".

## Admin map MVP — 2 of the 3 suggested items shipped

**Included:**

1. **Municipality camera for every assigned role.** `reporterHomeFocus` became
   `municipalityHomeFocus` and lost its `if (!isReporter) return null` gate, so municipal
   admins and responders now open on their own municipality like reporters already did.
   Concretely, the Cajidiocan admin opens at `{ lat: 12.4044, lng: 122.6897, zoom: 12 }`

   returns null for them and the public map is unchanged. The `requestId` prefix changed
   from `reporter-home:` to `municipality-home:`; nothing depended on the old string.
2. **`admin-dispatchable` no longer widens the map.** Its `mapFilter: 'all'` was removed
   rather than changed: the card counts verified + transferred and the rail has no single
   tab matching that pair, so any filter value would have shown the wrong pins. The card
   still opens its own panel with exactly its records; it just leaves the map filter alone.

**Excluded, and why:**

- **Sticky filter rail — deferred, and my earlier "1 class" estimate was wrong.** The rail
  lives inside the map `<section className="... overflow-hidden rounded-xl ...">`, and a
  sticky child of an `overflow-hidden` ancestor is clipped, so sticky does nothing there.
  Doing it properly means either moving the rail out of the map card (a visual redesign) or
  dropping the card's clipping and rounding the map canvas instead (a regression risk on the
  map's corners). Not MVP.
- **Aligning the rail's and the KPI strip's vocabulary** (rail splits Verified/Transferred,
  cards merge them; rail "Resolved" vs card "Resolved today"). Cosmetic, and it changes
  labels users read — a product call.
- **`MapLegend.jsx`** — still dead code, still awaiting the render-or-delete decision.

**Tests:** 2 added — "opens the map on the viewer municipality for every assigned role, not
just reporters" (asserts the focus prop for admin/responder/reporter and that guests stay
unfocused) and "does not widen the map filter when the dispatchable card is opened".
