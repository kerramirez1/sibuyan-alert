# 2026-09-17 — Sibuyan Alert

## Shipped: reach tracking (unique viewers per incident and per risk zone)

Option 1 of the design discussion in `2026-09-16.md`: "how many distinct people opened this
record's details", with risk zones included in the same mechanism. Full design, sizing
calculation and Data Privacy Act mapping are in **`docs/view-reach.md`** — that file is the
reference, this is the change record.

### Server

- **`server/models/ViewEvent.js`** (new) — collection `view_events`, one row per
  `(targetType, targetId, viewerKey)`. Polymorphic (`report` | `zone`) so incidents and zones
  share one dedupe rule. Three indexes: `uniq_target_viewer` (unique — THE dedupe),
  `ttl_last_viewed` (TTL, `VIEW_EVENT_RETENTION_DAYS = 180`), `reach_by_type_recent`.
- **`server/services/viewEventService.js`** (new) — `buildViewerIdentity`,
  `recordViewEvent` (upsert + one retry on E11000), `readReachByTargets`, `readTopReach`.
  No exported function can return a per-viewer list; that is a design constraint, not an
  accident.
- **`server/controllers/viewController.js`** (new) — `recordView` (POST /api/views) and
  `getReachLeaderboard` (GET /api/views/reach). Also keeps the legacy `Report.viewCount`
  counter alive so Accident History's "Views" column does not freeze.
- **`server/routes/views.js`** (new), mounted at `/api/views` in `server.js`.
- `reportViewLimiter` renamed to **`viewLimiter`** (it now serves both target types).
- `analyticsController.getAdminAnalytics` gained a scoped `reach` block.

### Client

- **`client/src/utils/viewerIdentity.js`** (new) — opaque `localStorage` uuid, with a manual
  RFC 4122 v4 fallback because `crypto.randomUUID` needs a secure context and this app is
  reachable over plain-HTTP LAN.
- **`client/src/hooks/useRecordView.js`** (new) — fire-and-forget, once per target per mount.
- **`client/src/hooks/useReachData.js`** + **`components/dashboard/ReachPanel.jsx`** (new) —
  the admin display, wired into `DashboardAnalyticsWorkspace`.
- Instrumented: `MapIncidentDetails` (report), `HighRiskZoneDetails` (zone),
  `AccidentHistoryPage` (migrated off `api.recordView`, which was then deleted).
- `api.recordViewEvent` attaches the anonymous id centrally so no surface can forget it.

### Two traps worth remembering

1. **Fake timers defeat a production timeout.** `getAdminAnalytics` bounds its reach lookup
   with a 2s `Promise.race` so a stalled aggregation cannot hang the endpoint. But
   `adminAnalyticsAccuracy.test.js` calls `vi.useFakeTimers()`, so that timer never fires and
   the real (unmocked) `ViewEvent.aggregate` hung all six tests for 60s. Fixed by mocking
   `ViewEvent` in that test with `importOriginal` so the real constants survive. The timeout
   is still correct for production — it just cannot be the thing that saves a fake-timer test.
2. **A fire-and-forget hook must not be able to throw.** The first `useRecordView` called
   `api.recordViewEvent(...).catch(...)` — but four client test files mock the api module
   without that new method, so the call threw *synchronously* inside the effect and took the
   panel down with it: **55 client tests failed**. Fixed with `?.` plus try/catch in the hook,
   which is also what its own doc comment promised. Telemetry must degrade, never break.

## BUG FOUND AND FIXED: every guest view was silently dropped (403 CSRF)

**Symptom:** opening a high risk zone as a guest produced no reach data at all. Signed-in
viewers worked, which made it look guest-specific and mysterious.

**Root cause — `server/middleware/csrf.js`.** `PUBLIC_CSRF_EXEMPT_PATHS` exempted the LEGACY
report-view path (`/api/reports/:id/views`) but not the new `/api/views`. The CSRF cookie is
only issued when a session is created (`authSessionService.js:99`, login/register), so an
unauthenticated guest has no cookie and no header to echo. `safeEquals(undefined, undefined)`
returns **false** by design (`if (!left || !right) return false`), so every guest POST was
answered **403 CSRF_TOKEN_INVALID** and dropped. The client is fire-and-forget, so it failed
silently. This also broke guest INCIDENT views, not just zones — same endpoint.

**The tell that was already in the codebase:** the legacy exemption carries the comment
*"Counter-only write with no auth side effects; guests must reach it."* Someone hit exactly
this before and recorded why. Adding a new guest-reachable POST without reading that list is
how it came back.

**Fix:** added `/^\/api\/views$/` to `PUBLIC_CSRF_EXEMPT_PATHS` with the rationale inline.
The origin check still applies, and the route keeps its own rate limiter.

**Regression guard:** three tests in `server/tests/viewReach.test.js` — a guest POST to
`/api/views` passes CSRF, the legacy path still passes, and `/api/reports` still gets 403 (so
the exemption did not widen anything else). **Verified by removing the exemption and watching
the first test fail**, then restoring it. A regression test that has never been seen to fail
is not yet a regression test.

**Test gap found along the way:** `client/src/test/HighRiskZoneDetails.test.jsx` mocked
`../services/api` with only `filesAPI` and no default export, while `useRecordView` imports
the default. The hook swallowed the missing method, so the suite was green while proving
nothing about whether the view was ever recorded. The mock now provides the default and two
tests assert the call — including one asserting it fires exactly once per mount even when the
zone object identity changes. **When a test mocks a module, it must mock the shape the code
actually imports, or a passing test can hide a dead feature.**

**Verification:** `npm run test:server` -> 329 pass, 1 pre-existing failure
(`iconAssetPaths.test.js`, missing `/icons/icon-192.png`, unrelated). Affected client tests ->
23 pass. Lint 0/0.

## Follow-up audit: is any OTHER guest-reachable write missing a CSRF exemption?

Audited every write route against the exemption list. **`/api/views` was the only real gap.**

| Guest-reachable write | Exempt? |
| --- | --- |
| `POST /api/auth/register`, `/login`, `/forgot-password`, `/reset-password/:token` | yes, `PUBLIC_AUTH_PATHS` |
| `POST /api/auth/logout` | yes, `LOGOUT_PATH` |
| `POST /api/reports/geocode` | yes |
| `POST /api/reports/:id/views` | yes |
| `POST /api/views` | **was missing — now fixed** |
| `POST /api/auth/refresh` | no, and correctly so: it needs a live session, so the caller always has a CSRF cookie |
| `reports` create/evidence, `highRiskZones` writes, `admin` writes, `notifications` writes | not guest-reachable (`protect` / `requireRole`) |

**Added a coverage guard** so the class cannot come back: `optionalAuth` is the marker that says
"a guest may reach this route", and every such route must be CSRF-exempt. The test parses
`server.js` for both the router imports AND the `app.use` mounts, rebuilds each full path, and
asserts the middleware lets it through — a route file only knows `/:id/views`, the middleware
sees `/api/reports/:id/views`, and guessing the prefix would make the guard lie. It asserts it
actually checked something, so a parsing failure cannot masquerade as a pass.

**Verified by disabling the exemption again:** the guard fails and names the route
(`["/api/views"]`). A coverage guard that has never been seen to fail is not yet a guard.

## Fixed the "pre-existing icon failure" — it was a real PWA bug, not a test quirk

`iconAssetPaths.test.js` had been failing since before this work started. It was reporting
`adminController.js -> /icons/icon-192.png`. Chasing it showed the test was the least of it:
**four icon files were missing, and `client/index.html` documents exactly why each one is
needed.**

Missing: `icon-192.png`, `icon-512.png`, `maskable-512.png` (all referenced by
`client/public/manifest.json`) and `apple-touch-icon.png` (referenced by `index.html`).

Why it mattered: `index.html` states the manifest is *"Required for installation and for Web
Push on iOS, which only delivers push to an installed home-screen web app."* With no icons the
install is broken, so **iOS Web Push cannot work** — for a rural emergency-alert app whose
whole notification story depends on residents installing it. `adminController.js` also uses
`/icons/icon-192.png` as the push notification icon, so those rendered broken too.

The intent was already written down in `index.html`, which is what made this fixable without
guessing:
- `icon-192` / `icon-512` — **transparent by design** (a comment explicitly warns not to
  repoint `apple-touch-icon` at them)
- `apple-touch-icon` — a **dedicated fully-opaque 180x180** variant, because *"iOS fills
  transparent pixels in apple-touch-icon with BLACK"*
- `manifest.json` declares `background_color: #ffffff`, which is the background to composite
  onto

Generated all four from `Alert.png` (1254x1254 RGBA, blue "S" mark with a red alert badge,
glyph bbox `(210,49,1079,1087)`):
- `icon-192` / `icon-512` — straight LANCZOS resize, transparency preserved
- `maskable-512` — opaque white, glyph at **70%**, inside the maskable safe zone (a launcher
  may crop to a circle of 80% diameter, so a square-ish glyph at full bleed would lose corners)
- `apple-touch-icon` — opaque white, glyph at 88%, near full-bleed like a normal app icon

Tooling note: **PIL was not installed.** Used the managed Python at
`~/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe` with a venv at
`~/.workbuddy-ai/binaries/python/envs/default`, then `pip install Pillow` into it — per the
runtime isolation rules, never a global install.

Verified visually (`scratch/icon-check.png`) on split light/dark backgrounds: the two "any"
icons show the dark field through them (genuinely transparent), the other two are solid
squares. `iconAssetPaths.test.js` now passes, so the server suite is fully green.
