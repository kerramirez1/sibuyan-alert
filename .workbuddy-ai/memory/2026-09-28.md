## Scoped the Risk zone reach leaderboard to the admin's municipality

**Task:** incident reach was already municipal, but zone reach read island-wide and
returned other municipalities' zone names on a municipal admin's dashboard.

### The change — `server/controllers/viewController.js` only

`getReachLeaderboard` already rejected a missing `assignedMunicipality` with 403 and
already scoped incidents via `buildMunicipalReportScope`. The zone branch was the only
thing reading unscoped:

```js
// before
readTopReach({ targetType: 'zone', limit })
// after
const [scopedReportIds, scopedZoneIds] = await Promise.all([
    Report.distinct('_id', buildMunicipalReportScope(municipality)),
    HighRiskZone.distinct('_id', { municipality }),
]);
readTopReach({ targetType: 'zone', limit, targetIds: scopedZoneIds })
```

No new service code was needed: `readTopReach` already accepted `targetIds` as an
allow-list, already applies it as `$match.targetId.$in` **inside** the pipeline before
`$sort`/`$limit`, and already returns `[]` for an empty array without querying. So the
scope lands before the limit for free — the thing to get right was resolving the ids and
passing them, not writing new aggregation logic.

`municipality` comes from `req.user.assignedMunicipality` and nowhere else. Query
parameters are read only for `limit`.

### Also updated

- The stale rationale comments: the doc block above `getReachLeaderboard` and the inline
  "Zones stay island-wide on purpose" comment both argued for the old behaviour and now
  explain the new one (map hazard visibility is untouched; this scopes the leaderboard,

- `server/tests/viewReach.test.js` — the "leaves the pipeline unscoped" test used

### Tests — `server/tests/reachLeaderboardScope.test.js`

Added `distinct` to the `HighRiskZone` mock (the controller now calls it). Header comment

**Verified: 64 files / 504 tests passing (server), lint 0/0.** Client untouched — the
frontend renders whatever the server returns and does no zone filtering of its own.

### Not changed, deliberately

- `routes/highRiskZones.js` and the island-wide `zones:island-wide` cache — the map's

- `readTopReach`'s `targetIds = null` unscoped mode — still a service capability, just

- No `isActive` filter was added to the zone allow-list: the requirement was to scope by
  municipality, and adding a liveness filter would have changed which zones appear beyond

### Tooling: headless Edge broke this session — read this before the next visual check

`--dump-dom` and `--screenshot` both stopped working mid-session, for two separate reasons
found by bisecting:

1. **Output path.** Writing the PNG into `scratch/` (OneDrive) silently produced nothing.
   Screenshots to `%LOCALAPPDATA%\Temp\...` work. Copy into `scratch/` afterwards with `cp`.
2. **Profile reuse.** A second invocation with the same `--user-data-dir` produces nothing.
   Every run needs a **unique** `--user-data-dir` (plus `--no-first-run`).

A single flaky run also just fails with no stderr and exit 0, so always **retry in a loop
until the output file exists** — do not trust the exit code. Working pattern:

```bash
"$EDGE" --headless=new --disable-gpu --no-sandbox --no-first-run \
  --user-data-dir="...\\edge-r$RANDOM$n" --hide-scrollbars --force-device-scale-factor=2 \
  --virtual-time-budget=8000 --screenshot="$OUT\\name.png" --window-size=$w,$h "$URL"
```

Also seen this session: `vite build` failing in `vite:prepare-out-dir` with
`[safe-delete] genie-trash ETIMEDOUT` — it empties `dist/` and then dies. Environmental, not
code: just re-run, the second attempt succeeds.
