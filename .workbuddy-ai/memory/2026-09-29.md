## Municipal administrator creates a responder account

### What already existed (so almost nothing new was needed)

- **Login already refuses an account with no password** (`authController.login`:
  `'No password set for this account. Please contact an administrator.'`). That IS the
  "prevent sign-in before setup" requirement — the new account is created with no password
  and is therefore inert. No new gate was added.
- **The reset flow is the invitation flow.** `forgotPassword` mints a 32-byte hex token,
  stores its SHA-256 hash plus a 1-hour expiry, and emails `/reset-password/{token}`;
  `resetPassword` hashes the incoming token and matches it. The invitation reuses all of it,
  so the emailed link is single-use (reissuing overwrites the secret) and time-limited for
  free, and the responder sets their own password through the page that already exists.
- **There is no AuditLog model.** The existing audit pattern is `verificationHistory` on the
  User (`{action, actor, feedback, at}`), so the new trail follows it.

### Security gap found and fixed

`getUsers` projects only `.select('-password')` and the schema had **no `select: false` on
`resetPasswordToken` / `resetPasswordExpires`** — so the municipal user list returned the
invitation secret (hashed, but still) on every row. Fixed at the schema level so no future
query can leak it by forgetting a projection, with a guard test.

### Files changed

| File | Change |
|---|---|
| `server/models/User.js` | `resetPasswordToken`/`resetPasswordExpires`/`createdBy`/`provisioningHistory` → `select: false`; new `recordProvisioningEvent({action, actor, municipality})` |
| `server/middleware/validate.js` | new `validateCreateResponder`; **rejects** a supplied `role`, `assignedMunicipality`, `password` rather than ignoring them |
| `server/controllers/adminController.js` | new `createResponder` + `resendResponderInvitation`; `issueResponderInvitation` helper; `toProvisionedResponderPayload` |
| `server/routes/admin.js` | `POST /users/responder`, `POST /users/:id/invite`, both `requireRole('municipal_admin')` |
| `server/services/emailService.js` | new `sendResponderInvitationEmail` (no credential in it — none exists) |
| `client/src/config/responderUnits.js` | **new** — client mirror of the canonical unit list (the server owns it; the client cannot import across the workspace) |
| `client/src/services/api.js` | `adminAPI.createResponder`, `adminAPI.resendResponderInvitation` |
| `client/src/pages/AdminUsersPage.jsx` | "Add responder" button + modal form with per-field errors, duplicate-email message, and a held-account retry when the mail fails |

### Design decisions

- **A mail failure is not a creation failure.** The account is kept (it is inert), the
  response is 201 with `invitationSent: false`, and the modal stays open holding the account
  with "Resend invitation" as the only remaining action. Deleting it would make a transient
  SMTP error cost a full restart.
- **Rejected, not ignored.** A client sending `role` or `assignedMunicipality` gets a 400.
  Silently dropping the field would let a cross-municipality or role-escalation attempt read
  as a success.
- The token and URL are **never logged** — the URL is the credential.

### Tests

`server/tests/createResponder.test.js` (21) and `server/tests/responderInvitationSecret.test.js`
(5), plus 5 added to `client/src/test/AdminUsersPage.test.jsx`.

Two test-harness gotchas worth remembering: express-validator middlewares are **async even
for synchronous rules**, so a chain walk must `await` each one or `handleValidationErrors`
runs before any rule has recorded a result; and the users page renders **every user twice**
(desktop table + mobile cards), so `findByText` on a name throws — use `findAllByText`.
