# 2026-09-30

## Responder invitation email — audit and fix

### The root cause

`sendEmail` (`server/services/emailService.js`) returned `success: true` for **any resolved
`sendMail`** and discarded `info.accepted` / `info.rejected`:

```js
const info = await transporter.sendMail(mailOptions);
return { success: true, messageId: info.messageId };
```

`sendMail` resolving means the SMTP transaction finished — not that the mail server accepted
the message for the intended recipient. A resolved send whose `accepted` list does not
contain the recipient is a message nobody received, and it was reported as delivered.

**Why it surfaced on invitations and not on password resets:** both flows share `sendEmail`,
but the reset flow only ever sends to an address the account already owns — an address that
has demonstrably worked before. The invitation sends to whatever the municipal administrator
just typed into the form, which is exactly where an unaccepted recipient appears. The bug was
always in the shared function; the invitation flow is simply the first caller whose recipient
is not pre-validated by reality.

### Nodemailer 9.0.3 behaviour, verified in `node_modules` (not assumed)

`lib/smtp-connection/index.js` around the RCPT TO handler:

```js
if (this._envelope.rejected.length < this._envelope.to.length) {
    ... this._sendCommand('DATA');          // resolves with { accepted, rejected }
} else {
    err = this._formatError("Can't send mail - all recipients were rejected", 'EENVELOPE', ...);
    return callback(err);                    // throws
}
```

So with a single recipient, an outright RCPT TO rejection throws (already handled), but a
**partially** accepted envelope resolves with the intended address in `rejected`. That
resolved-but-not-accepted case is the one that was silently reported as sent.

### The two failure modes, kept distinct

| | cause | what the admin is told |
|---|---|---|
| **1. Not accepted for the recipient** | `accepted` does not contain the address | "the mail server did not accept that recipient address" — re-check the address |
| **2. Accepted, link unusable** | `CLIENT_URL` missing/relative, or localhost in production | "the invitation link address (CLIENT_URL) is not set to the public client URL" |

Mode 2 was already fixed by a previous session (`server/utils/invitationUrl.js`, untracked at
the time — now committed). It is worth recording *why* it mattered: `forgotPassword` builds
its link from raw `process.env.CLIENT_URL` and sends regardless, so a bad `CLIENT_URL` still
produced an arriving reset email with a dead link; the invitation gate refuses to send at all.
That is a real behavioural difference between the two flows, and it is deliberate.

### Changes

- `server/services/emailService.js` — `sendEmail` now reads `info.accepted`/`info.rejected`,
  normalises addresses (bare vs `Name <addr>`), and returns
  `{ success: false, code: 'RECIPIENT_REJECTED' }` when the intended recipient is not in
  `accepted`. The check is deliberately **one-sided**: a transport that reports neither list
  yields no evidence and keeps the old behaviour, so a genuinely working send cannot break.
  The error string contains no address — it reaches an administrator and the log.
- `server/controllers/adminController.js` — maps `RECIPIENT_REJECTED` to its own
  administrator-safe sentence in `describeInvitationFailure`.

### Not touched

`forgotPassword` / `resetPassword` / `authController.js` — verified untouched via `git diff`.
Its anti-enumeration response is unconditional and stays that way.

### Tests

`server/tests/emailDeliveryResult.test.js` (8, new) covers accepted / partially accepted /
explicitly rejected / display-name normalisation / silent transport / no address leak /
throwing transport / unconfigured SMTP. Two added to `createResponder.test.js` for the
address-vs-server wording and for never echoing the address, link, or token.

### Deployment still needed

`CLIENT_URL` must be the public client origin in production. The local `server/.env` has
`CLIENT_URL=http://localhost:5173` with `NODE_ENV=development`, which is legitimate for local
work but means an invitation generated locally carries a link only the server machine can
open. `HEROKU_DEPLOYMENT.md` documents the production value.

## Follow-up audit: the "no recipient list" false positive

### What the transport can actually produce — settled from source, not assumed

The question was whether `sendEmail` could receive an `info` with **neither** `accepted` nor
`rejected`, which the first fix treated as "no evidence, keep success". Traced through
nodemailer 9.0.3 in `node_modules`:

- `smtp-connection/index.js` `_actionDATA` builds `const response = { accepted, rejected }`
  and calls `callback(null, response)` — so the `info` handed to `send()` always carries both.
- `smtp-connection/index.js` `send()` passes that `info` up, adding timing/`response` fields.
- `smtp-transport/index.js` adds `info.envelope` + `info.messageId` and resolves with it.
- DATA is only reached when `rejected.length < to.length`, so **a completed send always has
  `accepted.length >= 1`**.

**Conclusion: the configured SMTP transport cannot produce an absent or empty verdict.**
So that state is an anomaly, not a legitimate success — and the earlier "keep success"
fallback was itself the false positive. Changed to an explicit `DELIVERY_UNCONFIRMED`.

### Diagnostic codes now emitted

| code | meaning | whose problem |
|---|---|---|
| `URL_MISCONFIGURED` | CLIENT_URL missing/relative, or localhost in production | operator |
| `EMAIL_NOT_CONFIGURED` | SMTP_HOST/USER/PASS unset | operator |
| `RECIPIENT_REJECTED` | intended address not in `accepted` | administrator (typo) |
| `DELIVERY_UNCONFIRMED` | transport reported no verdict | mail provider |
| `SMTP_ERROR` / `DELIVERY_FAILED` | transport threw | mail provider |

Classification is **code-driven**; the old regex over the error text was removed, so the
service is the single owner of the verdict.

### Logging

`maskMailAddress` (`j***@example.com`) + the transport `messageId` as the correlation handle.
The privacy policy (`client/src/config/legal.js`) covers email as account data but says
nothing about logging it, so logs get the masked form only. No token, no URL, no credential.

### Forgot Password — checked, not assumed

`forgotPassword` **does** inspect its result and logs `'Password reset email failed:'`, but
returns `success: true` unconditionally — that is the anti-enumeration design, so its API
response is not proof of delivery. Left untouched. It also does NOT gate on CLIENT_URL, so it
can send an arriving email with a dead link, where the invitation refuses to send at all.

**No persisted server logs exist** in this repo (console-only). Historical sends cannot be
audited from the codebase; that needs the runtime stdout or the mail provider's logs.

### Tests

`emailDeliveryResult.test.js` now 10. One assertion **deliberately changed**: "keeps the
previous behaviour when the transport reports no recipient lists" expected `success: true`;
it is now "reports an explicit unconfirmed state…" expecting `DELIVERY_UNCONFIRMED`, with the
source evidence recorded in the comment. Also added: empty-both-lists, and masked-log
assertions. One `createResponder` fixture gained the `code` the service actually returns.

## Local audit: the failure was the .env load, not the SMTP path

Baseline given: **Forgot Password worked on the last Heroku deploy.** So this was a
local-only difference, and the first job was to prove or disprove a regression in the shared
email path.

### Ruled out, by measurement rather than reasoning

- **SMTP credentials are fine locally.** `verifyEmailTransport()` returned
  `{"success":true}` — "✅ Email service ready (SMTP verified)". It authenticates only; it
  sends nothing. So not an SMTP outage, and not a credentials problem.
- **The shared `sendEmail` path is NOT regressed.** Drove the real service through a fake
  SMTP server on `127.0.0.1` (no message leaves the machine):
  - RCPT TO accepted → `success: true`, `accepted: ['responder@example.test']`, `messageId`
    present. The acceptance check does not misfire.
  - RCPT TO rejected → Nodemailer **throws** `EENVELOPE` ("all recipients were rejected") →
    caught → `success: false`, `code: 'SMTP_ERROR'`.
  Note the rejected case classifies as `SMTP_ERROR`, not `RECIPIENT_REJECTED` — the
  all-rejected path throws rather than resolving, so that code is only reachable for a
  partial envelope. Worth revisiting, but it is not a regression.
- **`authConfig.js` reads env lazily** (all functions), so the ESM import-hoisting order in
  `server.js` (`dotenv.config()` at line 10, after the imports) is not a hazard for it. The
  email helpers are lazy too.

### Confirmed cause

`server/server.js` called **`dotenv.config()` with no path**, so dotenv resolved `./.env`
against `process.cwd()`. Measured, same probe, two working directories:

| cwd | `isEmailConfigured()` | `CLIENT_URL` | `sendEmail` |
|---|---|---|---|
| `server/` | **true** | `localhost:5173` | `success: true` |
| repo root | **false** | `<null>` (`CLIENT_URL_MISSING`) | `EMAIL_NOT_CONFIGURED` |

From the repo root nothing loads at all, and **both flows fail together** because both go
through `sendEmail` and both read `CLIENT_URL`. That is the "affects both flows" signature.

**Why Heroku was unaffected:** Heroku injects real environment variables, so dotenv never
matters there. Locally the load depended on how the server was started — `npm run dev` from
`server/` worked, `node server/server.js` from the root did not. That is exactly why the
failure looked intermittent.

### Fix

`dotenv.config({ path: resolve(dirname(fileURLToPath(import.meta.url)), '.env') })` — anchored
to the module, not the cwd. dotenv does not overwrite already-set variables, so a host that
injects config is unaffected either way. Verified from the repo root: `isEmailConfigured()`
now `true`, no missing vars.

### Secondary finding (not fixed — needs a decision)

`CLIENT_URL=http://localhost:5173` with `NODE_ENV=development` is allowed by design, so a
locally generated invitation is genuinely **sent and delivered** but carries a link only the
server machine can open. The admin sees `invitationSent: true`. That is failure mode 2
("accepted, link unusable"), and it is the one that would still bite after the .env fix.

### Tests

`server/tests/serverEnvLoading.test.js` (3, new) — guards against `dotenv.config()` with no
path reappearing, and asserts the anchored expression resolves to `server/.env`. The guard
strips comments first, because the fix's own explanatory prose quotes the bare form.

### Probes left in scratch/

`localSmtpProbe.mjs` (fake SMTP, accept/reject), `localConfigProbe.mjs` (presence +
transport verify, sends nothing), `localEmailFailureProbe.mjs` and `dotenvCwdProbe.mjs`
(the two-cwd comparison), `dotenvFixedProbe.mjs` (the fix, verified).
