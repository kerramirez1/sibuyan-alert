# 2026-10-17

## Codebase architecture inspection (Sibuyan Alert)

Read-only walkthrough, no code changed. Key findings:

- Monorepo via npm workspaces: `client/` (Vite + React 18 SPA, ~299 source files) and
  `server/` (Express + Socket.IO, ~195 source files). Single dyno on Heroku serves API + SPA.
- Server boot order in `server/server.js`: dotenv (path resolved from `__dirname`) →
  `validateRuntimeConfig` → Redis adapter (optional) → `connectDB` → seeds → readiness probes
  (barangay boundaries, hazard layers, analytics view) → background sweepers → static client.
- Auth: HttpOnly cookies only (`sibuyan_access` 15m, `sibuyan_refresh` 7d scoped to
  `/api/auth`, `sibuyan_csrf` readable). CSRF = double-submit + origin allowlist
  (`server/middleware/csrf.js`). Client 401 → single-flight refresh with `SESSION_ROTATING`
  retry backoff (`client/src/services/api.js`).
- RBAC: 4 roles (`ordinary`, `reporter`, `municipal_admin`, `responder`). No super-admin by
  design; municipality is the tenancy boundary, stored denormalized as a string.
- Report lifecycle: `pending → verified → responding → resolved`, plus `rejected` and
  `transferred` (transfer needs acknowledge from the receiving LGU).
- Realtime: Socket.IO rooms `user_<id>`, `reporters`, `municipality_<name>`,
  `municipality_<name>_responders`. Handshake-time auth, not lazy on `join`.
- Background loops: dispatch escalation sweeper (30s, ack window 5m, max 3 escalations),
  GridFS orphan sweeper (daily), evidence processing queue (serial), notification TTL.
- Domain extras: NOAH landslide hazard layers (registry-driven), derived accident hotspots
  (100m anchor clustering, 30-day window), face-detection evidence redaction.
- Docs: `CODEBASE_CONTEXT.md` is referenced by README/SYSTEM_PROCESSES but is **missing**
  from the repo root — only `SYSTEM_PROCESSES.md`, `README.md`, `AGENTS.md` exist.
- Tests: 131 client test files + 89 server test files.

## CONFIRMED PRODUCTION BUG (inspection only, no fix applied)

Commit `8c5a775` ("...client check inside startServer") moved
`configureProductionClient(app)` from module scope into `startServer()`. That places
`express.static` + the `app.get('*')` SPA fallback AFTER the module-scope terminal 404
handler (`server/server.js:440`). Express matches in registration order, so every
non-API GET in production — `/`, `/login`, `/assets/*.js` — is answered by the 404 JSON
handler. The SPA is unreachable in production; dev is unaffected because Vite serves it.

Verified empirically with a minimal Express repro: `GET /login` -> 404 `{"route":"not found"}`.
Test blind spot: `server/tests/clientApp.test.js` always builds a fresh app and calls
`configureProductionClient` first, so real stack order is never exercised.

Recommended fix (not yet applied): split registration from the throwing build check —
`registerProductionClient(app)` at module scope (before the 404), `assertProductionClientBuild()`
inside `startServer()`.

## ERR_ERL_KEY_GEN_IPV6 in middleware/rateLimiter.js (inspection only)

express-rate-limit 8.6.1. Two ValidationErrors at import (lines 68 and 95 — reportCreationLimiter,
reportEvidenceLimiter), caught by the lib's validator and only console.error'd; import completes.
Mechanism is **source-text inspection**: `keyGenerator.toString()` contains `req.ip` but not the
literal `ipKeyGenerator` -> throws. Not a runtime check, so extracting the helper call outside the
keyGenerator body still fails validation.

Severity correction: the IPv6 bypass is **latent, not live**. Both limiters sit behind `protect`
(`routes/reports.js:47`, `:60`, `:75`, `:76`), so `req.user` is always set and the IP fallback
branch is unreachable today. It becomes exploitable only if one is mounted without `protect`.

Fix: `import rateLimit, { ipKeyGenerator } from 'express-rate-limit'` and use
`ipKeyGenerator(req.ip)` inside each keyGenerator body. v4 returned unchanged, v6 -> /56 network.

## 18 unhandled "unexpected reply from redis client" in tests/rateLimiterPrefix.test.js

Root cause is the test double, not production. rate-limit-redis 4.3.1 RedisStore constructor
(index.mjs:91-92) assigns `this.incrementScriptSha = this.loadIncrementScript()` and
`this.getScriptSha = this.loadGetScript()` **without awaiting**. Both require a string SHA and
`throw new TypeError('unexpected reply from redis client')` otherwise. The fake client in the test
returns `Promise.resolve()` -> undefined -> 2 rejections per store x 9 limiters = 18. Constructor
can't await, so they surface as unhandled rejections; vitest reports them separately, tests pass.

Production is NOT affected — verified empirically: with the real ordering (connect() fire-and-forget
then sendCommand), node-redis queues the command while connecting and it stays pending, it does not
reject. Only an explicit disconnect/close rejects with ClientClosedError.

Fix: make the mock return a 40-char string for SCRIPT and [hits, ttl] for EVALSHA. Note the wrapper
in rateLimiter.js passes the command as ONE array arg to client.sendCommand.

### FIX APPLIED — 18 unhandled redis rejections in rateLimiterPrefix.test.js

Root cause: `rate-limit-redis@4.3.1`'s RedisStore constructor assigns two **un-awaited**
promises (`loadIncrementScript` / `loadGetScript`), each doing `SCRIPT LOAD` and throwing
`TypeError("unexpected reply from redis client")` unless the reply is a string. The test's
fake client returned `Promise.resolve()` (undefined) → 2 rejections per store × 9 = 18.
Constructor cannot await, so they surface as unhandled rejections. Test-only issue;
production is fine because `connect()` is already in flight and node-redis queues.

Fix (test file only, `server/tests/rateLimiterPrefix.test.js`):
- added `issuedCommands` array, reset in `beforeEach`
- fake `sendCommand(commandArgs)` now pushes the command and replies with the real shapes:
  `SCRIPT` → 40-char SHA string, `EVALSHA` → `[1, 60_000]`, else `null`
- new test asserts `SCRIPT LOAD` count === `createdStores.length * 2`

**Argument shape (verified in dist, matters if this mock is ever touched again):**
`RedisStore.sendCommand = async ({ command }) => sendCommandFn(...command)` — it destructures
then SPREADS. `rateLimiter.js` wraps as `(...args) => client.sendCommand(args)`, so the fake
client receives **one array** `['SCRIPT','LOAD',lua]`, not spread args. `EVALSHA` replies are
parsed by `parseScriptResponse` which requires a 2-element array.

**Verification:** 4/4 pass, `Errors` line gone entirely, 0 occurrences of "unexpected reply
from redis client", oxlint clean. Sibling suites (`reportRateLimit`, `rateLimiterIpv6Keying`)
still green — 13 total.

Note: the task brief said to expect the ERR_ERL_KEY_GEN_IPV6 warning on import, but that was
already fixed earlier the same day (committed as `368904a`), so the import now prints only
`ok`.
