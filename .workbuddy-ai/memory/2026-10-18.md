# 2026-10-18

## "Auto-locate times out even with signal" — diagnosis (inspection only, no code changed)

Two independent timeouts, neither caused by the cellular link.

**F1 (primary) — GPS acquisition asks for more precision than the app requires.**
`client/src/pages/ReportPage.jsx:645`:
`watchPosition({ enableHighAccuracy: true, timeout: 10000, maximumAge: 0 })`, with an app-level
12s watchdog at `:538-566`. `enableHighAccuracy: true` forbids a coarse network-derived fix, and
`maximumAge: 0` discards the last known position, so every attempt is a cold GPS fix. Indoors, in
a vehicle, or under tree cover that routinely takes 30-60s. Cellular signal is irrelevant to it.
Internal contradiction: `locationQuality.js:2` sets `GPS_MAX_ACCURACY_METERS = 100`, so a 100m fix
is accepted, yet acquisition demands maximum precision.

**F2 (secondary) — the reverse geocode has no client timeout, and the server serialises it.**
`client/src/services/api.js` sets no axios `timeout`; `reportsAPI.geocodeLocation` passes only a
`signal`. Server: `services/geocoding.js:3` `MIN_REQUEST_INTERVAL = 1000` plus one module-level
`requestQueue` promise chain (`:38`), so every Nominatim call from every user serialises 1s apart.
The Nth concurrent request waits ~(N-1)s before it even starts, plus up to 8s Nominatim timeout.
Bystanders reporting the same accident hit this simultaneously.

**F3 — rate limit.** `locationLookupLimiter` = 12/min/IP on `POST /api/reports/geocode`
(`routes/reports.js:35`). Pin dragging or a shared NAT burns it; a 429 surfaces to the user as
"Could not verify the barangay".

**Ruled out:** submit does not await geocode — `validateLocationStep` (`:286-294`) only blocks the
`confirming` state, and a GPS point alone satisfies validation, so a failed geocode never blocks
submission.

**Recommended:** two-phase acquisition (fast coarse `getCurrentPosition` first, then the
high-accuracy watch refines — the existing "Refining... (Xm)" UI already supports it) plus a 10s
timeout on the geocode request. Same option bug exists in
`components/reporterReports/QueuedReportLocationFix.jsx:152` (`enableHighAccuracy: true`,
`maximumAge: 0`, `timeout: 15000`).

**Limitation:** no physical device, so the F1/F2 ranking is inference from code + browser
semantics, not a captured trace.

### FIX APPLIED — two-phase acquisition + bounded geocode

`client/src/pages/ReportPage.jsx` only (plus two test files):

- Extracted the `watchPosition` success handler into `applyPosition`, declared inside
  `detectLocation()` after the 12s watchdog and before the watch. Body moved verbatim
  (including the pre-existing bare `{ }` block) so the `requestId` guard still opens it.
- Added a coarse pass before the watch:
  `geolocation.getCurrentPosition(applyPosition, () => {}, { enableHighAccuracy: false,
  timeout: 6000, maximumAge: 60000 })` — silent failure, the watch stays the authority.
- Watch options untouched (`enableHighAccuracy: true, timeout: 10000, maximumAge: 0`).
- Geocode now bounded: `{ signal: controller.signal, timeout: 10000 }` at `:447`. Axios
  rejects with ECONNABORTED (not ERR_CANCELED), so the existing catch already shows the
  "Could not verify the barangay" toast — the intended fallback.

Test updates: `getCurrentPosition: vi.fn()` added to both geolocation mocks
(`ReportPage.test.jsx`, `ReportPageAutosave.test.jsx`), and one new test in
`ReportPage.test.jsx` asserting the coarse fix reaches `MapView.selectedLocation` with the
watch never firing, then the precise fix supersedes it.

**Proof the test is meaningful:** against `HEAD`'s ReportPage.jsx it fails with
`expected "vi.fn()" to be called 1 times, but got 0 times`. Restored after.

**Verification:** 49 tests pass across `ReportPage` / `ReportPageAutosave` /
`QueuedReportLocationFix`; oxlint clean.

**Behavioural note (consequence of reusing `applyPosition`, not a bug I introduced):** a
coarse fix worse than `GPS_MAX_ACCURACY_METERS` (100m) sets `bestLocation`, so when the 12s
watchdog fires with no better fix it takes the `usable === false` branch and **clears** the
pin with "GPS accuracy is too low (Xm)". Before this change the same device got "Could not
determine location". The message is now more accurate, but a >100m network fix appears and
then disappears. Changing that would mean touching the accuracy-acceptance logic, which the
task forbade — flagged, not changed.

Still outstanding by design: `QueuedReportLocationFix.jsx:152` has the same cold-fix options
and was explicitly out of scope.
