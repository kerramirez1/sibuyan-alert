# 2026-10-18

## "Auto-locate times out even with signal" — diagnosis (inspection only, no code changed)

Two independent timeouts, neither caused by the cellular link.

**F1 (primary) — GPS acquisition asks for more precision than the app requires.**
`client/src/pages/ReportPage.jsx:645`:
`watchPosition({ enableHighAccuracy: true, timeout: 10000, maximumAge: 0 })`, with an app-level
12s watchdog at `:538-566`. `enableHighAccuracy: true` forbids a coarse network-derived fix, and
`maximumAge: 0` discards the last known position, so every attempt is a cold GPS fix. Indoors, in
a vehicle, or under tree cover that routinely takes 30-60s. Cellular signal is irrelevant to it.
Internal contradiction: `locationQuality.js:2` sets `GPS_MAX_ACCURACY_METERS = 100`, so a 100m fix
is accepted, yet acquisition demands maximum precision.

**F2 (secondary) — the reverse geocode has no client timeout, and the server serialises it.**
`client/src/services/api.js` sets no axios `timeout`; `reportsAPI.geocodeLocation` passes only a
`signal`. Server: `services/geocoding.js:3` `MIN_REQUEST_INTERVAL = 1000` plus one module-level
`requestQueue` promise chain (`:38`), so every Nominatim call from every user serialises 1s apart.
The Nth concurrent request waits ~(N-1)s before it even starts, plus up to 8s Nominatim timeout.
Bystanders reporting the same accident hit this simultaneously.

**F3 — rate limit.** `locationLookupLimiter` = 12/min/IP on `POST /api/reports/geocode`
(`routes/reports.js:35`). Pin dragging or a shared NAT burns it; a 429 surfaces to the user as
"Could not verify the barangay".

**Ruled out:** submit does not await geocode — `validateLocationStep` (`:286-294`) only blocks the
`confirming` state, and a GPS point alone satisfies validation, so a failed geocode never blocks
submission.

**Recommended:** two-phase acquisition (fast coarse `getCurrentPosition` first, then the
high-accuracy watch refines — the existing "Refining... (Xm)" UI already supports it) plus a 10s
timeout on the geocode request. Same option bug exists in
`components/reporterReports/QueuedReportLocationFix.jsx:152` (`enableHighAccuracy: true`,
`maximumAge: 0`, `timeout: 15000`).

**Limitation:** no physical device, so the F1/F2 ranking is inference from code + browser
semantics, not a captured trace.

## "Report views" accuracy / guest→login duplication (inspection only)

Two different numbers exist and they are NOT the same metric:

- **ViewEvent reach** (admin leaderboard): distinct viewers, deduped by the unique index on
  (targetType, targetId, viewerKey). Guest→login is collapsed by `collapseGuestViewForTarget`
  (viewEventService.js:117-135) and the reverse direction by `resolveViewerAlias`/`linkViewerAlias`
  (:158-208). This part is correct and well tested.
- **`Report.viewCount`** (what My Reports displays, `MyReportsPage.jsx:1105`): total opens,
  repeats included, documented as such in `viewController.js:44-50`.

So a guest opening a record 4× then logging in shows 5 in "Report views", not 1. The collapse
mechanism never touches `viewCount` — it only deletes ViewEvent rows. This is inherent to an
opens counter and cannot be fixed by collapsing.

Additional defect found: `getReportById` increments `viewCount` unconditionally
(`reportController.js:1157`) with **no owner self-view skip**, unlike the other two paths
(`reportController.js:1940`, `viewController.js:61`). Also `MapIncidentDetails.jsx` mounts both
`useOperationalIncidentDetails` (GET → +1) and `useRecordView` (POST /api/views → +1), so one map
open counts twice for a non-owner, once for the owner.

**Test conflict, must be respected:** `server/tests/getReportById.test.js:102,126,288,292` pins the
GET-side increment (test 11 is entirely about it failing non-blockingly). Removing that increment
requires rewriting those tests — do not treat it as a one-line change.

Recommended: display the deduped viewer count (batch aggregate over the listed report ids) instead
of `viewCount` in My Reports. Label change to "Report viewers" breaks
`client/src/test/MyReportsEvidenceViewer.test.jsx:207`.

### Follow-up designed (not implemented): make a GET stop writing viewCount

one line causes three defects at once: (a) one map open counts twice, because MapIncidentDetails

Test conflict, exact lines: `server/tests/getReportById.test.js:102` (test name), `:123-127`
(assertion), `:277,286-289` (test 10), and `:292-309` (test 11 exists solely to cover the failed
increment). Test 11 should be REPLACED by a `expect(updateSpy).not.toHaveBeenCalled()` guard, not
deleted — that is what stops the increment being reintroduced. `reportDetailReporterVerification
.test.js:51,111` only sets viewCount in fixtures, no assertion. Out of scope: the admin path still
increments at `adminController.js:771` (pinned by `reportViews.test.js:134`).

**Behavioural note (consequence of reusing `applyPosition`, not a bug I introduced):** a
coarse fix worse than `GPS_MAX_ACCURACY_METERS` (100m) sets `bestLocation`, so when the 12s

determine location". The message is now more accurate, but a >100m network fix appears and
then disappears. Changing that would mean touching the accuracy-acceptance logic, which the
task forbade — flagged, not changed.

Still outstanding by design: `QueuedReportLocationFix.jsx:152` has the same cold-fix options
and was explicitly out of scope.

### Distinct-viewer count on My Reports

Two different metrics existed: `Report.viewCount` (total opens, repeats + owner self-views
included on the GET path) and `ViewEvent` rows (deduped distinct viewers). My Reports was
showing the former.

- `server/services/viewEventService.js`: new `readViewerCountsForTargets({ targetType,
  targetIds })` → one `$match` + `$group { $sum: 1 }` aggregate returning a
  `Map<id, viewers>`; added to the default export. Row count IS the viewer count because
  the unique index on `(targetType, targetId, viewerKey)` allows one row per viewer.
- `server/controllers/reportController.js` `getMyReports`: one call per page, then
  `viewerCount` added inside the existing spread. `viewCount`, `evidence`, `evidenceCount`,
  `detailAccess`, `detailCompleteness` untouched — purely additive.
- `client/src/pages/MyReportsPage.jsx`: label `Report views` → `Report viewers`,
  `report?.viewCount || 0` → `report?.viewerCount ?? 0`.

**Verified claim in the brief:** owner self-views really do not create a ViewEvent row —
`server/controllers/viewController.js:62` skips when `viewerId === target.reporterId`, and
`recordReportView` matches. So criterion 4 holds.

**Test constraint worth remembering:** there is no `mongodb-memory-server` in this project
(and no new deps allowed), so a real "3 ViewEvent rows" integration test is impossible. The
new test in `server/tests/reportHideVisibility.test.js` stubs only
`ViewEvent.aggregate` via `vi.mock(..., async (importOriginal) => ({ ...actual,
default: Object.assign(actual.default, { aggregate: vi.fn() }) }))` — keeping the named
constants real, because the service validates `targetType` against `VIEW_TARGET_TYPES`.
That file's existing getMyReports tests pass `[]` from `Report.find`, so the early
`ids.length === 0` return means the aggregate is never called there and they needed no
change.

**Verification:** 15 server tests (`reportHideVisibility`) + 22 client tests
(`MyReportsEvidenceViewer`, `MyReportsPage`); oxlint clean on the three source files.

### GET /api/reports/:id no longer writes

`getReportById` used to fire an unconditional
`Report.updateOne({ $inc: { viewCount: 1 } })` on every read. Three defects, all
confirmed in the code: one map open counted twice (`MapIncidentDetails.jsx` mounts both
`useOperationalIncidentDetails` → GET and `useRecordView` → POST /api/views), owner

`reportController.js:1940` and `viewController.js:61`), and fallback/prefetch fetches
became views (`DashboardPage.jsx:438`).

- Removed the write, replaced with a comment recording why.
- Both payload branches now report the stored value: `viewCount: reportObj.viewCount || 0`
  / `report.viewCount || 0` (the speculative `+ 1` is gone).

Tests (`server/tests/getReportById.test.js`): test 1 renamed and its increment assertion
dropped (plus a new `viewCount` equals stored assertion), test 10's spy removed, test 11
replaced with a guard — `updateSpy` mocked with `.mockResolvedValue` so a regression fails
on `expect(updateSpy).not.toHaveBeenCalled()` rather than on a real DB attempt.

**Left alone on purpose:** `adminController.js:771` (admin GET still increments),
`recordReportView` (`reportController.js:1954`), `bumpLegacyReportViewCount`
(`viewController.js:66`). All three still bump and still skip the owner.

**Side effect worth knowing:** the admin dashboard's `stats.viewCounts` buckets
(`adminController.js:574-700`) aggregate `Report.viewCount`, so those totals will drop —
they now reflect only the explicit counting endpoints plus admin detail opens. That is the
corrected number, not a regression.

**Verification:** 19 tests pass (`getReportById` 12, `reportDetailReporterVerification` 2,
