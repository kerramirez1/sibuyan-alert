# 2026-10-19

## "0 of 5" evidence count only jumps to 5 at the very end — refresh problem, not persistence

New clue from the user: "0 of 5 kahit uploaded na ang apat, nung natapos ang lima saka lang nakita."
That rules out the GridFS-orphan / idempotency theory recorded on 2026-10-18: the photos DO persist,
they just never appear incrementally.

Links verified as NOT broken:
- `subscribe` (client/src/context/SocketContext.jsx:382) registers the callback directly on the
  socket for ANY event name, so `reportEvidenceUpdated` does reach
  `ResponderIncidentInspector.jsx:393`.
- `useOperationalIncidentDetails.load()` (133-167) fetches unconditionally and replaces
  `extraDetails`; `retry()` calls it with no `shouldLoad` guard.
- `toOperationalReport` includes `images` (server/utils/operationalReport.js:184), and the merge in
  `resolvedReport` (218-236) lets `extraDetails` win. No ETag on the admin detail route.
- Upload is sequential (`runFlush` is documented sequential, offlineReportQueue.js:761-779).

So the failing link is timing/ordering rather than wiring. Rather than guess a fourth time, the
robust fix is to stop depending on the round trip: the emit already carries `evidenceCount`,
`evidenceExpected` and `evidencePending`, so the drawer should patch its displayed report from the
socket payload immediately and still refetch in the background.

Design note: `IncidentDetailsContent` is only used by the admin drawer, so patching there cannot
leak to public surfaces. The override must reset when `reportId` changes, and must never lower a
count the refetch already reported (use max).

### FIX APPLIED — paint from the socket payload

`client/src/components/adminReports/ResponderIncidentInspector.jsx` only:

- `useMemo` added to the React import.
- `const [evidenceProgress, setEvidenceProgress] = useState(null)` beside `reportId`, plus a
  reset effect on `[reportId]` so a different incident never inherits the previous progress.
- The `reportEvidenceUpdated` handler now parses `evidenceCount` / `evidenceExpected` and calls
  `setEvidenceProgress` with **max-only** semantics (a refetch may already be ahead), then still
  calls `onRetryDetails()` — that remains the authoritative refresh for URLs and redaction state.
- `displayedReport` is a `useMemo` over `[report, evidenceProgress]` that overrides
  `evidenceCount` and `evidence` (`evidenceCount`/`count`/`expected`/`pending`/`uploadStatus`),
  with `received = max(progress, report.images.length)` and `pending = max(0, expected - received)`.
- `<IncidentDetailsContent report={displayedReport}>` — nothing else in that element changed.

**Test-harness gotcha:** `AdminEvidenceInspection.test.jsx` mocked `subscribe` as
`vi.fn(() => () => {})`, which discards the callback, so no event could be emitted. Replaced it
with a `vi.hoisted(() => ({ subscribers: {} }))` registry (the same pattern
`MyReportsPage.test.jsx` uses) and reset `socketMock.subscribers = {}` in `beforeEach`. `act`
had to be added to the testing-library import.

New test renders the inspector **directly** (not through `TestInspectorWithHook`) with a static
report and `onRetryDetails={retrySpy}`, so the assertion proves the paint does not depend on the
refetch — `retrySpy` resolves nothing.

**Proof the test is meaningful:** against `HEAD`'s component it fails with
`Unable to find an element with the text: Evidence photos (2 of 5)`. Restored after.
