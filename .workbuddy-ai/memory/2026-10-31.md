4. **`QueuedReportLocationFix.jsx:152` still uses `enableHighAccuracy: true, maximumAge: 0,

Performance levers, in order of perceived value:

- A visible "Use this location" action as soon as a usable fix exists, instead of always waiting
  the full watchdog — currently only <=30m stops early.
- On accuracy rejection, focus the map on the rejected fix instead of clearing everything, so the
  reporter can drag the pin from roughly the right place.

### Deleted reports reappearing on filter switch

Server side was correct (`adminController.js` hard `deleteOne`); the client cache was stale.

- `useIncidentReports.js`: `removeReport` now calls `clearQueryCache('incident-queue:')` after the
  state update. That single call covers all three callers — `deleteReport`, `dismissReport`, and
  the `reportDeleted` socket handler (line ~275) — because they all funnel through `removeReport`.
- `useIncidentActions.js`: both post-delete refreshes became
  `refreshReports({ silent: true, force: true })` so the refresh cannot piggyback an in-flight
  pre-delete response via `dedupedFetch`.

**Why the bug happened:** each filter combination has its own cache key, and `fetchReports` has a
fresh-cache shortcut (`if (!silent && !force)`) that returns with **no network call** while the
entry is under `QUERY_CACHE_TTLS.queue` (2 min). Removing a row from React state never touched the
cache, so switching filters rehydrated the pre-delete list.

**Checked before using it:** `clearQueryCache(prefix)` is prefix-matched over both the in-memory
Map and the persisted localStorage entries (`queryCache.js:150`), and with no argument it clears
*everything* — hence the explicit `'incident-queue:'` prefix.

**Tests:** two new cases in `useIncidentReports.test.jsx` — one asserting a filter switch after
removal triggers a real fetch, one replaying the reported flow (populate two filters → remove →
switch → deleted row gone, network call made). Both fail against `HEAD` with
`expected 2 to be greater than 2` (the cache answered instead of the network).

**Verification:** 22 tests (`useIncidentReports` 8, `IncidentQueue` 5, `IncidentQueueControls` 9);
oxlint clean.

## BUG FOUND — deleted reports reappear after switching filters

Server delete is a hard delete (`Report.deleteOne()`, adminController.js:1067), and the client is not
optimistic — `useIncidentActions.deleteReport` (252-272) awaits the API, then `removeReport(id)`, then
`refreshReports({ silent: true })`.

Root cause is the client cache. `useIncidentReports` caches the queue PER FILTER COMBINATION under
`incident-queue:<role>:<responderView>:<status>:<category>:p<page>:q<search>:f<focus>`
(key builder at useIncidentReports.js:11-13) with `QUERY_CACHE_TTLS.queue = 2 * 60 * 1000`
(queryCache.js:83).

`removeReport` (215-219) only updates React state — it never invalidates the cache. And
`fetchReports` has a fresh-cache shortcut (71-88) that RETURNS WITHOUT ANY NETWORK REQUEST while the
entry is under 2 minutes old. So switching to another filter rehydrates the pre-delete list and the
deleted rows reappear, with no fetch to correct them until the TTL expires.

Secondary: the post-delete refresh uses `dedupedFetch`, which can hand back an in-flight pre-delete
response and re-write the stale list into the cache.

Fix: `clearQueryCache('incident-queue:')` inside `removeReport` (covers delete, dismiss and the
`reportDeleted` socket handler, all of which call it), and pass `force: true` on the post-delete
refresh so it bypasses request dedupe. `clearQueryCache(prefix)` exists at queryCache.js:150 and
`refreshReports` is just `fetchReports` (useIncidentReports.js:427), which already accepts `force`.
